# 0005 — Auth and data implementation details

- Status: Accepted
- Date: 2026-10-07
- Refines: [0001](0001-tech-stack.md)

## Context

0001 chose Neon + Drizzle + Better Auth, deploying to Vercel first and a VPS later. Phase 1
needed the concrete shape: driver, ID strategy, verification policy, email delivery, and
where authorization lives.

## Decision

**Database.**

- Neon project `wanna-space` in `aws-ap-southeast-1` (Singapore), Postgres 18. Branches:
  `production` (default) and `development` (local work). Vercel functions should be pinned
  to `sin1` to sit next to the database.
- Driver: node-postgres (`pg`) `Pool` through Neon's pooled endpoint. It works identically
  on Vercel Fluid compute and on a VPS, so there is no driver swap when we move.
  Migrations use the direct (unpooled) URL.
- IDs: `uuid` columns defaulting to Postgres 18's `uuidv7()`. Better Auth's own ID
  generation is disabled (`advanced.database.generateId: false`) so every table, including
  auth tables, uses the same time-sortable IDs.
- Schema in `src/server/db/schema/*` with `casing: "snake_case"`; SQL migrations in
  `drizzle/`, generated by drizzle-kit and committed.

**Auth.**

- Better Auth with the Drizzle adapter; sessions live in our Postgres (30-day expiry,
  daily refresh, 5-minute signed cookie cache).
- Email + password requires verification before first sign-in. Verification and reset
  links are single-use and expire in 1 hour; a password reset revokes other sessions.
- Google OAuth is enabled automatically when `GOOGLE_CLIENT_ID/SECRET` are set; Google is a
  trusted provider for account linking (same verified email → same user).
- Rate limiting uses database storage so it holds across serverless instances.
- A `user.create.after` hook creates the personal space; the DAL also self-heals a missing
  space, so a failed hook can never lock a user out.

**Email.** Resend with react-email templates (`src/server/email/`). Sends use idempotency
keys derived from the token hash. In development without `RESEND_API_KEY`, emails are
printed to the server console; in production a missing key is a hard error.

**Authorization layers.**

1. `src/proxy.ts` — optimistic only: no session cookie on a room route → `/sign-in?next=…`.
   It never decides access and never redirects away from auth pages (a stale cookie would
   loop).
2. `src/server/dal.ts` — the real check. `requireUser()` / `requireSpace()` validate the
   session against the database; every query and action goes through them.
3. Auth pages call `redirectIfSignedIn()` server-side, using the same real check.

**Configuration.** `src/server/env.ts` validates env vars with zod on first use and fails
with a readable list; `features.google` / `features.email` gate optional integrations.

## Consequences

- Moving to a VPS is an env change plus `output: "standalone"`; no code paths differ.
- Pooled `pg` connections need sensible pool limits per instance (`max: 10`).
- Unverified accounts can't sign in, which adds friction but keeps the user table honest
  for a public SaaS.
